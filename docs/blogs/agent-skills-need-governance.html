02

The gap

Teams receive skills faster than they can trust them.

Public, generated, and evolved skills can guide tools, scripts, files, and team decisions. Distribution can deliver those candidates; it cannot decide whether this team should trust them before runtime.

The enterprise question is not only: where do we get skills? It is: which skills become trusted team memory?

[1]

Scale is already here

SkillsBench retained 47,150 unique public skills after deduplication. Volume is not hypothetical anymore.

[2]

Utility is not guaranteed

SWE-Skills-Bench found many public software skills gave no pass-rate gain, and some degraded performance.

[3]

Security risk is concrete

Snyk's ToxicSkills study reported critical-level security issues in 13.4% of scanned skills.

[4]

SKILL.md is a supply-chain surface

Recent work on semantic supply-chain attacks argues that skill metadata and instructions can steer agent selection and behavior.

03

The solution

Make every distributed skill carry an approved charter before runtime.

Skills Charter turns a Git repository into the review surface and source of truth for team-owned skill libraries. Each candidate receives a charter: source, owner, evidence, policy checks, approval state, install target, and runtime constraints.

Distributed candidate -> Skill Charter -> review -> approval -> runtime install.

Gate path From distributed candidate to trusted runtime asset
  1. 1
    Capture the distribution contextImport from marketplaces, public repos, generated folders, local agent directories, or docs.
  2. 2
    Attach provenance and evidenceOwners, source URLs, eval reports, trigger samples, risk labels, and review notes.
  3. 3
    Approve through Git and CIDiffs, checks, and history make skill changes visible and reversible.
  4. 4
    Install only approved packagesGenerate approved library views and install snippets for Codex, Claude Code, Copilot, and other clients.
04

The lifecycle

Agent skills have five layers. Skills Charter owns governance.

Creation produces candidates. Evaluation produces evidence. Distribution moves packages. Governance decides what a team should trust. Runtime loads and enforces approved skills.

Evaluation asks: does it work? Governance asks: should our team trust it?

01
Creation layerSkills come from hand-authored SOPs, generated packages, docs tools, and evolved traces.
02
Evaluation layerEvals, benchmarks, trigger tests, scans, and regression reports become review evidence.
03
Distribution layerMarketplaces, registries, verified catalogs, npx skills, and GitHub adapters move packages between teams and runtimes.
04
Governance layerSkills Charter owns provenance, ownership, policy checks, PR review, approval, rollback, and install trust.
05
Runtime layerClaude, Codex, Copilot, Cursor, allowlists, and MCP permissions load and enforce approved skills.

Creation, evaluation, and distribution create candidates. Governance turns the right candidates into approved team memory before runtime.

05

The roadmap

Build the gate. Then connect it everywhere skills move.

The demo proves the handoff from distributed candidate to approved runtime memory. Adapters make the charter gate usable inside existing teams, docs stacks, and agent clients.

Now

GitHub Pages manager

Browse candidate packages, edit SKILL.md, inspect risk, preview approved outputs, and hand off review-ready PRs.

Next

Adapters for existing tools

Connect the gate to Codex, Claude Code, GitHub Copilot, Cursor, GitBook, VitePress, MkDocs, Obsidian, Feishu, and Yuque.

Later

Evidence-aware intake

Import eval reports, skill-creator outputs, traces, and evolved candidates as review evidence instead of auto-publishing them.
